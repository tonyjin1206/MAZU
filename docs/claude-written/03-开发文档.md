## 二、目录结构详解

见《02-项目文档》第八节总览。开发时最常打交道的三个目录：

- `backend/app/routers/`：全部业务逻辑所在（本项目没有独立 service 层，路由函数即业务实现；`services/` 仅预警与汇率两块）。
- `backend/app/models/` 与 `schemas/`：按业务域一一对应拆分文件（auth/foundation/sales/purchase/production/inventory/tax_refund/system_config）。
- `frontend/src/views/<域>/`：每个后端模块对应一个前端子目录；公共表格页骨架在 `components/TablePageLayout.vue` / `SplitTablePageLayout.vue`。

## 三、后端开发规范

### 3.1 路由注册

1. 在 `routers/<域>.py` 定义 `router = APIRouter()`；
2. 在 `main.py::create_app()` 挂载：`app.include_router(xxx.router, prefix="/api/xxx", tags=["..."])`；
3. 基础档案类简单 CRUD 用 `foundation.py` 内的 `register_crud` 工厂批量注册（自带分页 list/get/create/update/delete + delete 保护钩子 + 可选 next-code 预览），不要重复手写。

### 3.2 权限（必须）

每个端点必须显式声明权限依赖，**不允许裸 `get_current_user`**（历史上因此出过 L4 越权事故）：

```python
from app.utils.auth import require_permission, require_any_permission

# 写端点：本域写权限
current_user: User = Depends(require_permission("menu:sales:orders"))

# 读端点：本域 + 业务引用域任一即可；禁止把 menu:inventory* / menu:production:batch / menu:dashboard 当引用域
current_user: User = Depends(require_any_permission(
    "menu:sales:orders", "menu:sales:invoices", "menu:sales:collections"))
```

惯例：每个 router 顶部集中定义 `XXX_READ_PERMS = (...)` 元组供读端点复用。仅管理员端点用 `Depends(get_current_admin)`。

### 3.3 Schema 定义

- Pydantic v2：`model_config = ConfigDict(from_attributes=True)`（不要用旧 `class Config`）。
- 命名三件套：`XxxCreate` / `XxxUpdate`（全可选）/ `XxxOut`。
- 简单实体的 Update 可省略，`register_crud` 会以 `dict = Body(...)` 兜底。
- 新增模型后 `Base.metadata.create_all` 只建表不加列——**改已有表结构必须写迁移脚本**（见 3.5）。

### 3.4 单据号与库存流水（强制走工具）

- 任何单据号用 `generate_doc_no(db, "XX", Model, "field_name")`；批次号用 `generate_batch_no(db)`（或带前缀 `generate_batch_no(db, prefix="FG")`）。函数内部先 `db.flush()` 再 MAX+1、生成后查重递增——循环生成时**不要绕过它**，否则会撞 UNIQUE。
- 任何库存变动必须同时写 `inv_inventory`（台账）与 `inv_transaction`（流水，含 before/after 数量与成本、`trans_no=generate_doc_no(db, "ST")`、source_doc_type/source_doc_no）。红冲/取消类操作要补冲销流水保留审计，不能物理删流水。

### 3.5 数据库迁移

无 Alembic 版本链（alembic 装了但未用于演进），实际做法是 `scripts/migrate_*.py` 幂等脚本 + `Base.metadata.create_all`：

- 新表：直接建模型，启动即建；
- 已有表加列/删列/改数据：在 `scripts/` 写幂等脚本（先检查列/表是否存在，重跑无副作用），参考 `migrate_batch2_finance.py`、`migrate_batch4_reminders.py`、`migrate_production_deoutsourcing.py`（重建表清理已删列并保数据）；
- 会破坏外键的操作注意 SQLite `foreign_keys=ON` 已开启。

### 3.6 种子数据

`main.py::lifespan` 每次启动执行：`_seed_rbac`（权限+7 角色+admin 用户，幂等，admin 恒补齐全权限）、`_seed_params`（字典，按分组幂等）、`_seed_currencies`（7 币种）、`seed_reminder_rules`（11 条提醒规则）。**新增权限码/字典/规则改这里**，不要另写初始化入口。另有 `ERP_DATA_DIR` 环境变量可重定向数据目录（测试隔离的关键）。

### 3.7 后台任务

lifespan 内两个 asyncio 任务：`_daily_rate_task`（每日 09:00 拉汇率）、`_daily_reminder_task`（启动补扫一次 + 每日 09:00 账期扫描）。失败静默次日重试；停服随 lifespan 取消。

## 四、前端开发规范

### 4.1 API 调用

- 统一走 `src/api/`：`request.js` 是 axios 实例（baseURL `/api`、30s 超时、**camel↔snake 自动转换**、401 清缓存跳登录、422 透传后端 detail）；`foundation.js` 提供 `crudApi(prefix)` 工厂（list/get/create/update/delete/select）；各业务域方法集中在 `business.js`（salesApi/purchaseApi/productionApi/outsourceApi/inventoryApi/taxRefundApi/notificationApi…）。**页面禁止散写 `request.get(...)`**（架构检查脚本 `scripts/check_architecture.py` 可验证）。
- 后端返回的 `{total, page, page_size, items}` 是列表页标准结构。

### 4.2 页面与路由

- 新页面：`views/<域>/Xxx.vue` + `router/index.js` 加路由并**必须带 `meta: { perm: 'menu:xxx' }`**（路由守卫据此拦截无权限访问）；菜单在 `components/Layout.vue` 按权限码渲染，两处权限码必须一致。
- 列表页优先用 `TablePageLayout`（查询区/工具栏/表格/分页骨架）+ 列设置 composable（localStorage 键 `mazu_*`）。
- 确认弹窗文案要写清后果（本项目的确认框均带业务后果说明，如「已认领 N 种材料将退回原批次」）。

### 4.3 构建

`npm run build` = `tsc && vite build`。产物需放到 `backend/frontend_dist/` 由后端托管（SPA fallback 到 index.html，前端路由用 history 模式）。

## 五、数据库设计要点

- 表名前缀 = 模块（`sys_/fd_/so_/ar_/po_/ap_/mo_/os_/inv_/tr_`），字段 snake_case；金额类同时保留外币 `*_fc` 与本位币两套；单据状态用中文枚举字符串（如 `待审核/已审核`），**状态判定一律以代码内实际字符串为准**（models/routers 里可搜）。
- 全模型清单与核心字段见《02-项目文档》第三节。
- 关键 ER 链：
  - 销售主链：`fd_customer → so_order → so_order_item`（三分支字段 `production_status`）`→ so_delivery → so_invoice → ar_account → ar_collection(_alloc)`；
  - 采购链：`so_order_item / po_requisition → po_order(_item) → po_receipt(_item) → po_invoice → ap_account → ap_payment(_alloc)`；
  - 生产链：`so_order_item → mo_production → mo_production_material / mo_production_process / mo_material_issue → mo_receipt`；
  - 委外链：`so_order_item → os_order(每工序一张, process_id) → AP；os_claim_material`（订单级认领）；
  - 库存核心：`inv_inventory`（批次台账）+ `inv_transaction`（全部出入库流水，含成本快照）+ `inv_stock_in`（待入库单）+ `inv_stocktake(_item)`；
  - 退税链：`po_invoice → tr_input_invoice → tr_declaration_row ← so_customs_item`。
- 外键在 SQLite 层强制开启（PRAGMA），删除上游前必须先处理下游（代码里大量 delete-guard 即为此）。

## 六、API 接口示例

> 交互约定：除 login 外均带 `Authorization: Bearer <token>`；业务错误 400/404/409 + `{"detail": "中文提示"}`。

### 6.1 登录

```http
POST /api/auth/login
{ "username": "admin", "password": "admin123" }

200 → { "access_token": "eyJ...", "user": { "id": 1, "username": "admin", "role_code": "admin", ... } }
401 → { "detail": "用户名或密码错误" }
```

### 6.2 创建销售订单（多明细行）

```http
POST /api/sales/orders
{
  "customer_id": 1,
  "order_date": "2026-08-31",
  "currency_id": 2, "exchange_rate": 7.1,
  "payment_terms": "TT",
  "items": [
    { "product_id": 3, "quantity": 1000, "unit_price": 2.5 },
    { "product_id": 4, "quantity": 200,  "unit_price": 12.0 }
  ]
}

200 → { "id": 12, "order_no": "SO-26083101", "message": "..." }
400 → { "detail": "数量必须大于0" }
```

### 6.3 销售明细三路分流（审核后，行级互斥）

```http
POST /api/sales/order-items/{item_id}/stock-in     # 转直采 → 明细「已通知入库」
POST /api/sales/order-items/{item_id}/outsource    # 转外发 → 明细「已通知外发」
POST /api/sales/order-items/{item_id}/re-produce   # 转生产 → 生成 MO，明细「生产中」
```

互斥：已处于任一路线状态的行再次分流返回 400；未审核订单分流返回 400。

### 6.4 销售订单转采购（按供应商拆单）

```http
POST /api/purchase/orders/from-sales
{
  "sales_order_id": 12,
  "loss_pct": 10,
  "rows": [
    { "sales_item_id": 21, "material_id": 5, "supplier_id": 2, "quantity": 1100, "unit_price": 8.5, "tax_rate": 13 }
  ]
}

200 → { "message": "已生成 1 张采购订单", "orders": [{ "order_no": "PO-26083101", "supplier_name": "...", "item_count": 1 }] }
400 → { "detail": "xxx 采购数量超过需求数量×（1+损耗10%）..." }   # 需求 = 订单数 × BOM 用量 ×(1+损耗)，后端硬校验
```

### 6.5 采购入库（批次+流水自动生成）

```http
POST /api/purchase/receipts
{
  "order_id": 8, "warehouse_id": 1, "receipt_date": "2026-08-31",
  "items": [ { "order_item_id": 31, "material_id": 5, "quantity": 500 } ]
}

200 → { "id": 6, "receipt_no": "PR-26083101", "message": "入库成功，共 1 项，已生成批次号" }
```

副作用：批次 `YYYYMMDD-NNN` 入 `inv_inventory`、`purchase_in` 流水入 `inv_transaction`、材料 `purchase_price` 回写、订单状态推进（部分入库/待开票）、关联外购 MO 状态推进。注意：明细若已 `receive_type`（转成品库/原料库）会被 400 拦截（双轨防重复）。

### 6.6 待入库单收货（stock-in 双轨收货）

```http
POST /api/stock-in/{id}/receive
{ "warehouse_id": 2, "quantity": 300, "receive_date": "2026-08-31" }

200 → { "message": "收货 300，单据状态：部分入库" }   # 收满自动「已入库」并回写销售明细/委外单
```

### 6.7 发票 → 应付/应收自动生成

```http
POST /api/purchase/invoices
{ "order_id": 8, "invoice_no": "12345678", "amount": 4000, "tax_amount": 520,
  "invoice_type": "增值税专用发票", "invoice_date": "2026-08-31" }

200 → { "id": 4, "invoice_no": "12345678", "ap_no": "AP-26083101", "message": "发票已创建，应付已生成" }
```

副作用：可抵扣类型自动同步 `tr_input_invoice`；生成 AP（到期日 = 发票日 + 供应商账期，默认 30 天）。重复发票号 → 409。

### 6.8 收款核销

```http
POST /api/sales/collections
{ "customer_id": 1, "amount": 5000, "collection_date": "2026-08-31", "ar_account_ids": 7, "payment_method": "银行转账" }

200 → { "message": "收款成功" }   # CR 单号；核销额 = min(amount, AR 余额)，可负数=退款
```

### 6.9 驾驶舱

```http
GET /api/dashboard                       # cash_in/cash_out（近6月）、ar_aging、ap_aging、profit
GET /api/dashboard/profit-detail/{product_id}
GET /api/dashboard/net-cash-detail/2026-08
```

### 6.10 AI 对话

```http
POST /api/chat/message  { "message": "帮我查一下杭州客户的应收", "session_id": "admin" }
```

## 七、测试指南

### 7.1 后端 pytest

- **必须用 `./test.sh` 跑**：它清空代理/PYTHONPATH 环境变量，并指定全新临时 `ERP_DATA_DIR`，绝不触碰开发库。
- `conftest.py` 复用 `app/main.py::_seed_rbac` 作权限种子单一数据源；测试数据统一由 `tests/test_data.py::build_foundation()`（session 级 fixture）通过 API 构建共享档案——**新测试禁止自建档案**，复用/扩展构建器即可（这是 README 明文规范）。
- 测试文件按域组织：`test_textile_flow.py`（单订单全流程主链）、`test_three_branch.py`（三分支互斥矩阵）、`test_state_machine.py`、`test_inventory_v2.py`、`test_sales_return_red.py`（红冲链）、`test_reminders.py`、`test_rbac_l4_extended.py`（越权矩阵）、`test_migration_production.py`（迁移幂等）等，共 285 用例（当前全绿）。
- 状态机测试用「(单据, 动作) → 文档池」复用单据，避免库内单据爆炸。

### 7.2 E2E（Playwright）

- `e2e/conftest.py` 自起后端（8789，临时库）+ vite（5174，`VITE_PROXY_TARGET` 指回 8789）+ Chromium headless；
- 每个用例自动收集 **console 错误 / pageerror / 失败网络请求** 三类信号（vite HMR、devtools、favicon 等已知噪音白名单过滤）；
- 套件：`test_smoke_pages.py`（逐页冒烟）、`test_core_flow.py`、`test_l2_interaction.py`、`test_rbac_menu.py`、`test_matsu_assistant.py`，共 59 用例。

### 7.3 新增测试的约定

1. 权限相关断言不要硬编码权限数量（admin 权限数动态等于权限码总数）；
2. 涉及状态流转先看 `test_state_machine.py` 是否已有同款文档池；
3. 跑全量 `./test.sh` 确认 0 failed 后再提交。

## 八、已知技术债务

1. **无数据库版本链**：迁移靠幂等脚本手工执行，新环境拉代码后需确认跑过哪些 `scripts/migrate_*.py`（启动 create_all 只覆盖「新表」）。可考虑引入 Alembic（依赖已装）。
2. **业务逻辑集中在 routers**：`sales.py` 约 2900 行、`purchase.py` 约 2000 行，路由函数直接写业务；缺 service 层与单元级拆分，改核心流程需要较强的回归测试兜底（现有 285 用例即为此服务）。
3. **超量收货不拦截**（known-issues #3/#4，用户确认遗留）：采购入库与完工入库不校验累计数量超订单量，靠人工核对。
4. **未发布代码仍在库**：报关界面（`menu:sales:customs`）与退税界面（`menu:tax`）前端页面存在但路由未注册、权限码被 `_seed_rbac` 清理；后端 API 完整。启用时需恢复权限码 + 路由 + 菜单三处。
5. **生产模块残留**：加工费发票（`mo_processing_invoice` + `ProcessingInvoices.vue`）在纯自产定线下创建恒 400、候选恒空，页面仍在路由中（菜单隐藏）；`os_order_material`、`mo_outsourcing` 为历史保留表。
6. **前端类型检查形同虚设**：`build` 里带 `tsc` 但源码主体为 JS，仅少量 .ts；`src/counter.ts`、`main.ts` 与 `main.js` 并存属脚手架残留。
7. **AI 会话内存态**：`bot_chat.py` 的 SessionStore 存进程内存，重启即失（另有 `sys_bot_conversation` 表未接入该路径）；多 worker 部署时会话不共享。
8. **仓库类型双命名**：历史数据存在「成品仓/原料仓」与「成品仓库/原辅料仓库」两套取值，`stock_in.py` 已做双集合兼容，新代码应统一用参数字典里的两值。
9. **汇率任务静默失败**：每日 09:00 拉取失败不告警仅日志，需人工关注或手动「获取最新汇率」。
