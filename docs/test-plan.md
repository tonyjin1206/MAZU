# MTS 外贸ERP 自动化测试方案

> 目标：自动化测试完成后，用户在浏览器人工操作时基本不出现因前后端匹配、校验缺失导致的报错；设计逻辑（按钮显隐、单据状态）有测试背书；杜绝"只测合理数据"的盲区；代码符合单一数据源等架构规范。

---

## 一、现状诊断（已发现的问题）

### 1.1 前后端契约缺口（已实锤 3 处）

| 前端调用（business.js / Vue 页面） | 后端 | 影响 |
|---|---|---|
| `GET/POST/PUT/DELETE /production/outsourcings` | ❌ 无路由、无模型 | 委外工单页面（Outsourcings.vue）打开即报错 |
| `GET/POST /production/outsource-receipts` | ❌ 无路由（仅 OutsourceReceiptItem 模型） | 委外入库（ProductionReceipts.vue）失败 |
| `POST /production/material-issues` | ❌ 仅有 `GET .../material-issues/{material_id}` 详情 | 生产领料创建失败 |

**这就是"人工浏览器测试才暴露基础报错"的直接原因**——前端页面/接口先行，后端缺失时编译期和运行时都不会自动发现。

### 1.2 测试现状

| 层 | 现状 | 缺口 |
|---|---|---|
| 后端 pytest | 5 文件（基础/数据/权限/纺织流程） | 无契约测试、无状态机测试、边界数据覆盖弱 |
| 健壮性脚本 | scripts/test_robust.py（手工跑，模拟"合理"数据） | 不是 pytest，不进 CI；离谱数据覆盖不足 |
| 前端 | 无任何测试 | 无契约/组件测试 |
| CI | 仅后端 pytest + flake8 | 前端、契约、E2E 均未接入 |
| 设计逻辑 | 无测试 | 状态流转、按钮显隐全靠人工点 |

## 二、测试分层架构（逻辑主线）

```
┌─────────────────────────────────────────────────────┐
│  第 1 层：契约测试（前后端一致性）← 需求 1 的根治     │
│  前端 API 调用清单 ⇄ 后端路由清单 自动比对            │
│  不匹配 → 测试失败 → 提交前拦截                      │
├─────────────────────────────────────────────────────┤
│  第 2 层：状态机测试（设计逻辑）← 需求 2              │
│  每张单据：状态枚举 × 可用操作 = 合法/非法矩阵        │
│  参数化验证：非法流转必须被拒绝                       │
├─────────────────────────────────────────────────────┤
│  第 3 层：边界数据测试（离谱输入）← 需求 3            │
│  负数/零/超大/超长/null/非法枚举/XSS/SQL注入          │
│  验收标准：4xx 拒绝或安全处理，绝不 500               │
├─────────────────────────────────────────────────────┤
│  第 4 层：E2E 测试（真实浏览器）← 需求 1 的最终保障    │
│  Playwright：登录→建档→销售→采购→生产→入库 全流程     │
│  模拟用户真实操作，验证页面可打开、按钮显隐正确        │
├─────────────────────────────────────────────────────┤
│  第 5 层：架构规范性检查 ← 需求 4                     │
│  表结构单一数据源、无冗余表、前端 API 封装统一         │
└─────────────────────────────────────────────────────┘
```

**逻辑说明**：契约测试管"接口对得上"，状态机测试管"业务规则对"，边界测试管"烂数据杀不死系统"，E2E 管"真实用户点得通"。前四层全绿 = 人工操作基本不会报错；第五层管长期健康。

---

## 三、分阶段实施

### 阶段 0：契约测试（立即见效，先做）

- **做法**：写一个 pytest 测试，启动 FastAPI TestClient，自动扫描：
  1. 前端 `src/api/*.js` 里所有 `request.get/post/put/delete/patch` 调用
  2. 后端所有 `@router.Xxx` 路由
  3. 比对：路径、HTTP 方法是否一一对应
- **产出**：`backend/tests/test_contract.py` + 契约清单文档 `docs/api-contract.md`（每个接口：前端调用处、后端路由、状态）
- **验收**：上述 3 处缺口被测试自动捕获（先标记为已知问题，修复或确认后转绿）
- **工作量**：约 200 行 pytest

### 阶段 1：状态机测试（设计逻辑背书）

- **做法**：从后端代码提取每张单据的状态流转规则，生成"状态 × 操作"矩阵：

  | 单据 | 状态枚举（从代码提取） | 操作 |
  |---|---|---|
  | 生产订单 | 待确认/待排产/已排产/生产中/已完成/部分入库/已入库/待采购/采购中/已关闭 | 确认、排产、发料、完工、入库、关闭、推PR… |
  | 采购订单 | 待审核/已审核/部分入库/已完成/已关闭 | 审核、入库、关闭… |
  | 销售订单 | 待审核/已审/生产中/部分发货/已发货/已完成/已关闭 | 审核、发货、报关… |
  | 采购申请 | 待处理/已转单/已关闭 | 转单、关闭 |

- **做法**：参数化测试——对每个操作，遍历所有状态，验证「合法流转成功、非法流转被拒绝(4xx)」
- **产出**：`backend/tests/test_state_machine.py` + 状态流转矩阵文档 `docs/state-flow.md`
- **验收**：任意非法状态流转（如未审核就入库）必须返回错误
- **工作量**：约 300 行

### 阶段 2：边界数据测试（离谱输入）

- **做法**：对每个写接口（POST/PUT）注入离谱数据，pytest 参数化：

  | 输入类型 | 例子 | 期望 |
  |---|---|---|
  | 负数/零 | 数量=-1、金额=0 | 4xx 拒绝 |
  | 超大 | 数量=999999999 | 4xx 或安全处理 |
  | 超长 | 255+ 字符字符串 | 4xx 或截断 |
  | 空值 | 必填字段=null / 空串 / 纯空格 | 4xx |
  | 类型错误 | 数字字段传 "abc" | 422 |
  | 非法枚举 | status="乱写的状态" | 4xx |
  | 注入 | XSS 脚本、SQL 注入字符串 | 原样存储或转义，不崩溃 |
  | 越权 | 低权限角色调高权限接口 | 403 |
- **产出**：`backend/tests/test_boundary.py`（升级替换 scripts/test_robust.py 的手工做法）
- **验收**：所有离谱输入返回 4xx 或正确处理，**0 个 500**
- **工作量**：约 250 行

### 阶段 3：E2E 测试（真实浏览器）

- **做法**：Playwright + pytest，真实起前后端，走完整业务流程：

  ```
  登录 → 建档(客户/供应商/物料/产品/BOM/工序) → 销售报价/订单
  → 生产订单(自产/委外/外购) → 推采购申请 → 转采购订单 → 采购入库
  → 生产发料/完工/入库 → 销售发货 → 收款/付款 → 退税申报
  ```

- **每个页面**：打开不报错（捕获前端 console 错误 + 网络 4xx/5xx）、按钮显隐符合状态、增删改查可用
- **产出**：`e2e/` 目录（Playwright 测试）+ 执行报告
- **验收**：全流程走通，页面 0 网络错误、0 console 错误
- **工作量**：最大头，约 500-800 行，分模块逐步加

### 阶段 4：架构规范性检查（单一数据源）

- **做法**：写一个审查脚本 `scripts/check_architecture.py`：
  1. 表结构检查：是否存在功能重复的表（如"委外商独立表"这类过度设计）
  2. 前端 API 封装检查：所有页面必须走 `src/api/*.js` 统一封装，禁止页面内散写 request
  3. 路由命名检查：前后端路径风格一致
- **产出**：审查报告 + 接入 CI
- **验收**：报告 0 个架构违规
- **工作量**：约 150 行

### 阶段 5：接入 CI（.github/workflows/ci.yml）

- 增加 job：契约测试 + 边界测试 + 状态机测试（后端）；前端 build + 契约（前端）
- E2E 视情况接 CI（本地先跑通）

---

## 四、实施顺序建议

| 顺序 | 阶段 | 为什么这个顺序 |
|---|---|---|
| 1 | 阶段 0 契约测试 | 立即暴露所有前后端匹配问题，成本最低收益最高 |
| 2 | 阶段 1 状态机 | 设计逻辑是用户最担心的，纯后端可测 |
| 3 | 阶段 2 边界数据 | 与 0/1 共用测试基建，顺手补齐 |
| 4 | 阶段 4 架构检查 | 静态脚本，快 |
| 5 | 阶段 3 E2E | 最重，放最后做，前面层绿了 E2E 才有意义 |
| 6 | 阶段 5 CI 接入 | 全部稳定后自动化 |

---

## 五、需要用户确认的事项

1. **委外工单缺口**：`/production/outsourcings` 等 3 组接口后端缺失——是后端还没开发完（本分支工作的一部分），还是设计上已废弃该页面？这决定契约测试是把它们标为"已知问题"还是立即修复。
2. **E2E 的浏览器**：本机 Windows 装 Playwright 需要下载 Chromium（约 150MB），是否接受？
3. **范围**：先做阶段 0-2（后端全覆盖，最快见效），还是按顺序一路做到 E2E？

## 六、批2 销售退货财务层 专项测试（已落地）

> 依赖 SP 流程调整后已适配；对应分层架构中的「状态机/业务规则 + 边界数据」层。

**测试文件：** `backend/tests/test_sales_return_red.py`（6 场景，随批2 一并落地）

| # | 场景 | 断言 |
|---|---|---|
| 1 | 蓝字开票 + 上限校验 | 全额开票成功；再开超未开票金额 → 400"超过未开票金额" |
| 2 | 红字发票链路 | 红冲成功（全额负数 + 原票标记已红冲）；红字票禁改（PUT 400）禁删（DELETE 400）；已红冲蓝字票禁删；列表带 `is_red`/`red_of_invoice_id`；红字应收 `is_red=1`、`balance<0` |
| 3 | 重复红冲拦截 | 原票已红冲后再红冲 → 400；红字票不能再红冲 |
| 4 | 退款登记 | 负数收款核销红字应收（余额向 0 靠拢）；退超 → 400"超过可退余额" |
| 5 | 核销转移 | 红字→同客户正余额成功（写 `ar_adjustment`）；超上限 → 400"超过可转移上限"；跨客户/源非红字拦截 |
| 6 | 退货联动 + 负数申报 | 已报税退货打标 `refund_declared=1`；`return-candidates`/`return-adjustments` 添加负数行并重算出口额 |

> 建议：将此文件接入全量回归与 CI（backend-test job）；后续批3 报关单明细化、批4 预警系统另建专项文件，遵循同一 conftest + test_data 单一数据源规范。

## 七、批4 预警提醒系统 专项测试（已落地）

> 依赖 SP 流程；按当前产品逻辑重校（无生产订单模块，销售订单下游走转直采/转外发）。通知落库即视为已发（D7）。

**测试文件：** `backend/tests/test_reminders.py`（6 场景，随批4 一并落地）

| # | 场景 | 断言 |
|---|---|---|
| 1 | 规则种子 | 规则应≥10（6 事件+4 定时）；无 MO_PLANNED/MO_OUTSOURCED；含 SO_TO_PURCHASE/SO_TO_OUTSOURCE/AR_CREATED/AR_OVERDUE |
| 2 | 事件埋点 SO_APPROVED | 审核后生成通知发给销售经理；标题含订单号 |
| 3 | 去重 | 同一单据同提醒点 1 小时内只 1 条 |
| 4 | AR_CREATED 双收件人 | 应收生成 → 财务+销售各 1 条 |
| 5 | 定时扫描 | 应收将到期/逾期分别落库；**红字应收不参与**；逾期通知销售+财务 |
| 6 | 通知 API | unread-count 返回 count；admin-query 返回 items+total（管理端） |

> 基建：`test.sh` 本次改为**隔离测试库**（每次全新临时库，不复用可能陈旧/含数据的 `backend/data/erp.db`）；`conftest.setup_db` 补种提醒规则；`reset_local_db` KEEP 补 `sys_reminder_rule`/`sys_notification`。建议接入 CI（backend-test job）。
