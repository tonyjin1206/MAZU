# 委派循环工作流 — 通用方案草案（待确认）

> 目标：让"你定目标 → 我拆任务 → 执行者开发 → 我审目标偏离 → 我调任务 → 执行者优化 → 我验收汇报"成为**可接续、可循环、随时启停、过程可视化**的通用工作法。不局限 ERP/代码，覆盖所有复杂可拆解任务。

## 一、核心理念（为什么这样设计）

1. **任务 ≠ 对话**：复杂任务是一次有状态、可恢复的工程，不是聊天窗里的一次性往返。状态落在**持久化看板（SQLite）**上，中断后能接续。
2. **执行者 ≠ 决策者**：执行者（可能是 codex / 子代理 / AI，统称「执行车道」）只产出产物（diff / 文档 / 数据）。**它不拥有 Kanban 生命周期、不做最终验收、不动看板状态**——这些全归协调者（我，Hermes）。
3. **目标偏离是常态，不是例外**：复杂任务中执行车道必然偏离目标。所以循环必须内建「**审目标偏离 → 重新拆卡 → 再派**」的回路，而不是一次跑到底。
4. **允许你拍板偏离**：偏离不违规——**只要报给你**。协调者有权基于专业判断做偏离调整，但每个偏离都记录、上报、可回溯。

## 二、循环模型（核心）—— 四阶段九站

```
  ┌─────────────────────────────── 主循环 ─────────────────────────────────┐
  │                                                                        │
  ▼                                                                        │
【① 定目标】→【② 拆任务】→【③ 建卡入板】→【④ 派执行】→【⑤ 执行产出】
                                                                        │
  ▲                                                                        ▼
【⑨ 汇报】←【⑧ 验收】←【⑦ 再审】←【③' 重拆卡】←【⑥ 审目标偏离】
  │                     │             │◄── 发现偏离 ──│
  └─────────────────────┴─────────────┘
```

| 站 | 名 | 谁 | 做什么 | 落点 |
|---|---|---|---|---|
| ① | **定目标** | 你 + 我 | 对齐「要什么结果」：可执行、可验收、有边界 | 写进卡 body 的目标段 |
| ② | **拆任务** | 我 | 按依赖/文件/风险拆成原子卡；同文件改→串行(parent-child)，异文件→并行(sibling)；每个卡带**验收标准 + 文件范围 + 禁碰项 + 验证命令** | 多张卡 |
| ③ | **建卡入板** | 我 | `hermes kanban create --workspace worktree --project <slug> --branch <br> --priority 1 --body <完整门槛> --idempotency-key <key>` | 看板 |
| ④ | **派执行** | 我 | 隔离 worktree + 派执行车道（codex exec 或 delegate_task）；附**简报**（范围/禁碰/验证命令/参考规则/输出要求） | 隔离 branch |
| ⑤ | **执行产出** | 执行车道 | 只产出产物（diff/文档/数据）；不调 kanban 工具 | 产物 |
| ⑥ | **审目标偏离** | 我 | **双重审核**：(a)代码/产物对不对；(b)**是否偏离你的原始目标**。后者是核心——逐条对照①的目标 | 偏离记录 |
| ⑦ | **再审/救回** | 我 | 偏离→要么改派重做，要么重拆卡（③'）；轻微→我直接修；严重且违背目标→**报你** | 卡状态 |
| ⑧ | **验收** | 我 | 独立复跑验证命令（不信执行者自报）；达标才 `kanban_complete` | 卡 done |
| ⑨ | **汇报** | 我 | 结果/偏离/风险/后续，给「验收汇报」 | 汇报 |

## 三、关键机制（满足你四条诉求）

### 1. 可接续 ✅
- 卡的 body 里**必须写死**：目标、验收基线数字、文件范围、禁碰项、验证命令。
- 执行车道的**简报持久化**到 `/tmp/<task_id>-brief.md`（不是只存在我 memory），中断后从简报+看板可完整恢复上下文。
- 看板是 SQLite 持久化，`hermes kanban runs <id>` 可随时查每次执行历史、OUTCOME、Comments（含阻塞根因）。

### 2. 可循环 ✅
- **⑥审偏离 → ⑦救回 → ③'重拆卡 → ④再派** 是内建回路（见上图分支），不是线性一次。
- 每次循环的产物/结论**写回卡 comments**，形成可回溯的迭代记录。

### 3. 随时启停 ✅
- 启动：`hermes kanban dispatch`（或 gateway 自动调 ready 卡）。
- 停止：`kanban_block` 或回收；**心跳超时的 stale 卡自动 reclaim**，不永久卡死。
- 中途任何时刻，`hermes kanban show <id>` 即可看到卡到哪一步、谁负责、卡在哪。

### 4. 过程可视化 ✅
- **kanban 板**：状态/流程/依赖一目了然。
- **本设计图**（archify architecture）：展示主循环 + 偏离回路 + 审批门。
- 每张卡的 `kanban_heartbeat` 记录"执行车道正改哪个文件/卡在哪个步骤"。

## 四、通用化要点（不局限 ERP/代码）

这套循环的**输入是"目标"，输出是"符合目标的可交付物"**，与具体领域解耦：
- 代码任务：产物=diff，验证=./test.sh
- 文档/调研任务：产物=文档，验证=内容/引用核对（用 `analysis-delegation` 执行车道）
- 数据/报表任务：产物=数据表/报表，验证=数据一致性抽查
- 命名规范：执行车道 = codex / 子代理 / 任意 agent；协调者 = Hermes 固定
